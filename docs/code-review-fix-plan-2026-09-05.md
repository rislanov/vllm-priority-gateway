# План исправлений по результатам ревью кода

Дата: 5 сентября 2026 года. Проверенный коммит: `0e5393dfb349e7650f42e51c1919539244ce12e6` (`origin/main` после обновления удалённых ссылок). Ветка ревью: `codex/code-review-plan-2026-09-05`.

Найдено **6 подтверждённых проблем: 2 уровня P1 и 4 уровня P2**. Ниже — сценарии отказа, причины, шаги исправления и критерии приёмки. Исправления рабочего кода в рамках этого ревью не выполнялись.

## Область и способ проверки

Проверены код запуска и остановки gateway, публичный API, авторизация, admission, routing, proxy и разбор usage, мониторинг, circuit breaker, registry, SQLite и миграции, аналитика, Admin API и встроенный веб-интерфейс. Дополнительно просмотрены служебные команды и конфигурация сборки/развёртывания. Документация использовалась для уточнения ожидаемого поведения.

Существующие `*_test.go` и каталог `tests/` исключены из ревью; замечаний к тестам и их покрытию нет. Критерии приёмки ниже описывают проверку будущих исправлений.

Инструменты Codebase Memory MCP в сессии недоступны: установить проект графа, поколение и проверить `check_index_coverage` не удалось. Поэтому использованы непосредственное чтение исходников и прослеживание вызовов; полнота графового индекса не предполагается.

`go build ./...` успешно выполнен на Go 1.27.0, darwin/arm64. Проблемы воспроизведены отдельными локальными диагностическими программами: с настоящим HTTP-обменом для потока, production-компонентами для ожидания/отзыва ключа и drain, временной копией production-кода для гонки публикации и SQLite. CSRF проверен на точной копии middleware с обработчиком, читающим токен тем же способом, что и HTML-renderer. GPU, реальный vLLM и развёртывание Docker в ходе ревью не запускались.

## Очерёдность

| Порядок | Приоритет | Исправление | Основное последствие |
|---|---|---|---|
| 1 | P1 | Передавать клиенту обрыв уже начатого ответа | Незавершённая генерация выглядит как штатно завершённый HTTP-ответ |
| 2 | P1 | Исключить применение устаревшего списка backend | Успешные изменения конфигурации могут оставить пул без работающего мониторинга |
| 3 | P2 | Повторно проверять ключ после ожидания до admission | Запрос начинает inference после отзыва ключа во время ожидания |
| 4 | P2 | Сохранять учёт активных запросов при drain | Admin API преждевременно сообщает нулевой inflight у backend |
| 5 | P2 | Устранить конфликт повышения SQLite-транзакции до пишущей | Корректные административные изменения отклоняются на фоне записи аналитики |
| 6 | P2 | Передавать новый CSRF-токен первому HTML-renderer | Первая отправка формы после прямого входа на страницу получает 403 |

P1 — исправить в первую очередь из-за потери корректности ответа или доступности inference. P2 — исправить в следующем цикле работ; условия возникновения указаны для каждого замечания.

## 1. [P1] Завершать оборванный поток как ошибку транспорта

**Места:** [internal/httpapi/public.go:138–144](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/httpapi/public.go#L138-L144), [internal/gateway/forward.go:308–315](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/gateway/forward.go#L308-L315), [internal/proxy/proxy.go:219–229](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/proxy/proxy.go#L219-L229).

**Сценарий и последствие.** Backend отправляет HTTP 200 и один SSE-фрагмент, затем обрывает chunked-соединение до окончания генерации. Proxy обнаруживает `unexpected EOF` и записывает ошибку в `Result.Err`. Но `Service.Forward` формирует `APIError` только до начала ответа, а публичный обработчик отбрасывает сам `Result`. Обработчик возвращается обычным образом, и HTTP-сервер корректно завершает downstream-ответ. Клиент, который ориентируется на ошибку HTTP-потока, не получает сигнала о потере продолжения генерации.

**Воспроизведение.** Использованы `fakevllm.ResetAfterChunks`, реальный `PublicHandler`, `Service`, `Proxy` и локальные HTTP-соединения:

```text
Прямой запрос к backend: status=200, read_error=unexpected EOF
Тот же обрыв через gateway: status=200, read_error=<nil>
llmgw_requests_total{client="review",model="public",priority_class="normal",status_class="2xx"} 1
```

В обоих ответах отсутствует `[DONE]`. Дополнительно [forwardLifecycle.finish:39–57](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/gateway/forward.go#L39-L57) не переносит ошибку начатого ответа в событие завершения; причина сбоя теряется в логах и не увеличивается `llmgw_backend_failures_total`.

**План исправления:**

- [ ] Сохранить результат `Service.Forward` в публичном обработчике и явно обработать ошибку после `ResponseStarted`.
- [ ] После завершения учёта запроса аварийно завершать HTTP-поток, например через `http.ErrAbortHandler`, с учётом действующего middleware. Не пытаться дописать JSON-ошибку в уже начатый SSE и не повторять запрос после отправки данных.
- [ ] Передавать в событие завершения отдельную ограниченную классификацию ошибки upstream body; сохранять фактически отправленный HTTP-статус, но учитывать неуспешное завершение в логах и метриках. Отмену со стороны клиента учитывать отдельно.

**Критерий приёмки.** После первого фрагмента и аварии upstream клиент видит неполный HTTP-ответ/ошибку транспорта, продолжение не повторяется на другом backend, все leases освобождаются один раз. Телеметрия отражает ошибку потока. Полный ответ продолжает завершаться без ошибки. Проверить HTTP/1.1 и HTTP/2, если он включён на входе.

## 2. [P1] Не позволять старой публикации откатывать runtime backend

**Места:** [internal/httpapi/admin.go:365–382](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/httpapi/admin.go#L365-L382), [internal/monitor/manager.go:75–105](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/monitor/manager.go#L75-L105).

**Сценарий и последствие.** Два административных запроса публикуют изменения параллельно. Первый получает snapshot R1 и приостанавливается перед `Reconcile`. Второй публикует R2 с новым backend и запускает его worker. После этого первый передаёт старый список R1 в `Reconcile`, который удаляет новый worker. Registry остаётся на R2, оба запроса могут завершиться успешно, но backend из актуальной конфигурации перестаёт мониториться и исключается из маршрутизации. Если он единственный доступный в пуле, запросы получают 503 до следующей публикации конфигурации.

Registry защищает монотонность revision, но runtime получает только список backend без номера ревизии. Mutex внутри manager не обеспечивает порядок отдельных публикаций.

**Воспроизведение.** Настоящие SQLite, Registry, AdminService и Manager; управляющая задержка добавлена перед первым вызовом `Reconcile` во внешней обёртке:

```text
После новой публикации: revision=3, registry_backends=1, circuit="closed"
После задержанной старой: revision=3, registry_backends=1, circuit="", runtime_state="unhealthy"
```

**План исправления:**

- [ ] Сериализовать участок `Reload → Snapshot → Reconcile → setDegraded` единым механизмом публикации. Как альтернатива — передавать revision в runtime и отклонять устаревшие применения.
- [ ] Согласовать состояние `degraded` с результатом последней актуальной публикации, чтобы старый вызов не перезаписывал его.
- [ ] Сохранить проверку соответствия конфигурации backend при получении lease.

**Критерий приёмки.** При задержке R1, полном применении R2 и последующем продолжении R1 registry и runtime соответствуют R2; новые workers сохраняются, удалённые не восстанавливаются, admission использует актуальные backend. Проверить также параллельные drain/resume и изменение URL.

## 3. [P2] Проверять актуальность ключа после ожидания перед admission

**Места:** [internal/gateway/forward.go:246–276](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/gateway/forward.go#L246-L276), [internal/analytics/recorder.go:139–145](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/analytics/recorder.go#L139-L145), [internal/gateway/forward.go:175–180](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/gateway/forward.go#L175-L180).

**Сценарий и последствие.** После аутентификации запрос может ждать место в `Recorder.ReserveResponseComplete`: стандартная ёмкость составляет 1024 reservations. Пока все места заняты, оператор отзывает ключ. После освобождения места запрос проходит admission и отправляется upstream, поскольку текущие проверки повторно проверяют клиента, пул и доступ к модели, но не ключ. Сам inference начинается уже после отзыва. Аналогичное окно существует для истечения срока действия ключа.

Это касается запросов, уже ожидавших до отзыва; новые запросы с отозванным ключом корректно получают 401. Прерывание уже выполняющихся генераций для исправления этой проблемы не требуется.

**Воспроизведение.** В настоящем Recorder заняты 1024 reservations; запрос остановлен на входе в ожидание, выполнен `Registry.MarkKeyRevoked`, затем освобождено одно место:

```text
Повторная ValidateAPIKey: 401
Ответ ранее ожидавшего запроса: 200
Новых запросов на backend после отзыва: 1
```

**План исправления:**

- [ ] После потенциально длительного ожидания повторно проверить ключ и получить актуальную политику клиента непосредственно перед admission.
- [ ] При отказе завершить reservation без отправки upstream и без утечки ёмкости Recorder.
- [ ] Определить такую же проверку для выбора альтернативного backend, если перед повторной попыткой ключ уже отозван или истёк.

**Критерий приёмки.** Ключ отозван или истёк во время ожидания — после разблокировки запрос получает 401 и не создаёт upstream-запрос. Без отзыва запрос проходит штатно. Места Recorder и счётчики admission возвращаются в исходное состояние.

## 4. [P2] Сохранять активные backend leases при drain и обновлении настроек

**Места:** [internal/monitor/manager.go:76–102](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/monitor/manager.go#L76-L102), [internal/monitor/manager.go:255–275](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/monitor/manager.go#L255-L275).

**Сценарий и последствие.** `Reconcile` сравнивает целиком `domain.Backend`. Изменение `Draining`, настроек или только `UpdatedAt` заменяет worker. Новый worker начинает с `GatewayInflight=0`, а ещё выполняющиеся запросы продолжают держать callbacks старого worker. Поэтому Admin API показывает ноль активных gateway-запросов к backend сразу после Drain, хотя генерация продолжается. Оператор, проверяющий завершение drain через этот показатель API, может преждевременно остановить vLLM. При Resume до их окончания маршрутизатор также получает заниженный inflight.

**Воспроизведение:**

```text
AcquireBackend → GatewayInflight=1
Reconcile(Draining=true) → GatewayInflight=0
Исходный lease всё ещё удерживается, callback завершения ещё не вызван
```

Проблема относится к backend runtime-счётчику, используемому Admin API и routing. Счётчик inflight пула хранится отдельно и не обнуляется; HTML-dashboard показывает именно его, а у backend — upstream-метрику Running. У метрики `llmgw_backend_requests_inflight` отдельный учёт через observer; он не доказывает корректность runtime-счётчика.

**План исправления:**

- [ ] Отделить число активных leases от заменяемого worker мониторинга либо учитывать активные leases предыдущих поколений до их завершения.
- [ ] Для изменения drain и служебных полей не терять информацию об уже назначенных запросах.
- [ ] Сохранить защиту от влияния завершений старого поколения на circuit нового upstream при смене URL; простой перенос всех callbacks в новый breaker некорректен.

**Критерий приёмки.** При одном активном запросе после Drain счётчик остаётся равным 1, новые запросы не назначаются; после завершения он становится 0. Resume и обычное редактирование не обнуляют текущую нагрузку и не дают отрицательных значений. Смена upstream не смешивает результаты circuit разных поколений.

## 5. [P2] Устранить отказы административных UPDATE при записи аналитики

**Места:** [internal/store/clients.go:61–82](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/store/clients.go#L61-L82), [internal/store/pools.go:55–73](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/store/pools.go#L55-L73), аналогичный `UpdateBackend` в `internal/store/backends.go`. Классификация ответа: [internal/httpapi/admin.go:607–618](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/httpapi/admin.go#L607-L618).

**Сценарий и последствие.** Методы начинают deferred SQLite-транзакцию, читают `created_at`, затем выполняют UPDATE. Если между чтением и записью успевает завершиться запись аналитики, читающий snapshot уже нельзя повысить до пишущего: корректное изменение возвращает `SQLITE_BUSY`. Повтора всей транзакции нет. Дополнительно API по умолчанию превращает эту ошибку хранения в `400 validation_error`, хотя данные запроса корректны. Настройка `busy_timeout=5000` не устраняет этот конфликт snapshot.

**Воспроизведение.** На настоящем store параллельно выполнены 1500 `UpdateClient` и 1500 `InsertUsageBatch`:

```text
failed_admin_updates=91/1500
first_error="update client: database is locked (5) (SQLITE_BUSY)"
failed_analytics_batches=0
```

Число отказов зависит от планирования конкурентных операций; 91 — результат конкретного запуска, а не оценка доли отказов в production.

**План исправления:**

- [ ] Для изменяющих транзакций захватывать право записи до первого SELECT (`BEGIN IMMEDIATE`), либо начинать операцию с UPDATE и получать поля через `RETURNING`.
- [ ] Если выбран повтор при contention, повторять всю транзакцию с ограничением по context, сохраняя атомарность сущности, access и revision.
- [ ] Применить решение ко всем CRUD с чтением перед записью; не сериализовать без необходимости аналитические чтения.
- [ ] Отделить временные ошибки хранения от ошибок валидации и возвращать соответствующий серверный статус.

**Критерий приёмки.** При управляемой записи между чтением и UPDATE операция успешно завершается после разрешения конфликта либо возвращает корректную временную серверную ошибку по достижении лимита ожидания. Параллельная нагрузка не порождает ложные `validation_error`; изменения и revision остаются атомарными.

## 6. [P2] Заполнять CSRF-токен при первом открытии формы

**Места:** [internal/httpapi/admin_auth.go:63–80](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/httpapi/admin_auth.go#L63-L80), [internal/httpapi/admin_auth.go:137–140](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/httpapi/admin_auth.go#L137-L140), [internal/web/web.go:395–400](https://github.com/rislanov/vllm-priority-gateway/blob/0e5393dfb349e7650f42e51c1919539244ce12e6/internal/web/web.go#L395-L400).

**Сценарий и последствие.** Пользователь без cookie `llmgw_csrf` напрямую открывает `/admin/clients`, `/admin/keys` или `/admin/backends` и проходит Basic auth. Middleware генерирует токен и добавляет его в `Set-Cookie` ответа, но не передаёт обработчику. `web.render` читает cookie исходного request, поэтому скрытое поле `csrf_token` остаётся пустым. При отправке формы браузер уже имеет cookie, но отправляет пустое поле; сервер отвечает 403. Повторное открытие страницы устраняет симптом. JavaScript не заполняет токен вместо сервера.

**Воспроизведение:**

```text
Первый GET: status=200, rendered_token="", cookie_count=1
Первый POST: status=403, body="CSRF token mismatch\n"
```

**План исправления:**

- [ ] Передавать валидированный или только что созданный токен в request context перед вызовом следующего обработчика.
- [ ] Читать этот токен в `AdminCSRFToken`, чтобы первый HTML-ответ содержал то же значение, что и cookie.
- [ ] Сохранить отклонение отсутствующего/неверного CSRF на изменяющих запросах.

**Критерий приёмки.** Первый authenticated GET страницы формы без cookie возвращает непустой hidden token, совпадающий с установленной cookie. Последующий корректный POST проходит без обновления страницы; неверный или отсутствующий токен по-прежнему даёт 403.

## Организация исправлений

- [ ] Выполнить пункты 1–2 первыми, отдельными изменениями с проверкой описанных сценариев.
- [ ] Затем исправить пункты 3–6. Изменения публикации и drain согласовать между собой, поскольку оба затрагивают жизненный цикл backend.
- [ ] Для каждого пункта приложить результат воспроизведения до исправления и результат того же сценария после него.
- [ ] После интеграции проверить сборку и штатные сценарии: успешная потоковая генерация, отказ admission, отзыв ключа, изменение конфигурации, drain/resume и создание сущностей в админке.

Это список подтверждённых дефектов в проверенном срезе, а не гарантия отсутствия других ошибок. Ссылки на строки закреплены за проверенным коммитом и не зависят от последующих изменений ветки.
